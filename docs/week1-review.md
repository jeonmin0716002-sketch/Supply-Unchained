## 2. 문승준 님께

### 2-1. 먼저 — 잘 만든 코드입니다

- **`collector`(I/O) / `features`(순수 로직) / `scorer`(가중치) 분리가 정확합니다.**
  덕분에 통합할 때 손댈 게 거의 없었습니다. 공용 fetcher로 바꾸는 것도 `collect()` 내부만
  갈아끼우면 끝났고, 테스트 15개는 무수정으로 통과했습니다.
- **자기 신호의 재현율을 직접 측정해서 문서에 적은 것** — OSSF 악성 패키지 11,545개로
  typosquat 재현율이 6.5%임을 재고, "실제 악성의 90%는 typosquat가 아니다"라고 쓰셨습니다.
  이건 발표에서 **멀티레이어 설계의 근거** 그 자체입니다. 심사위원이 "왜 레이어가 3개냐"고
  물으면 답이 이미 준비돼 있는 셈입니다.
- **`has_release_burst`의 비율 기반 설계** — naive하게 "24시간 내 3개"로 짰으면 성숙한
  패키지가 바쁜 하루를 보낸 것도 전부 걸렸을 겁니다. 테스트에도 그 케이스가 있습니다.

### 2-2. 통합하면서 이미 고친 것 (승준 님 코드가 바뀌었습니다)

`common/pypi.py` 공용 fetcher를 만들면서 `collector.py`의 다운로드 부분이 대체됐습니다.
`_sdist_has_setup_py()` 와 `_find_sdist_url()` 은 **삭제**됐습니다.

| 고친 것 | 왜 |
|---|---|
| 크기 제한이 **다운로드 중**에 동작 | 기존엔 `resp.content`로 전부 받은 **뒤에** 검사 → 거대 sdist에 메모리 폭발. 악성 패키지를 분석하는 도구가 악성 패키지에 당하는 구조였음 |
| `.zip`/`.whl`/`.bz2`/`.xz` 지원 | `mode="r:gz"` 고정이라 다른 포맷은 `TarError` → `except` → 조용히 `has_install_script=False`. **재현율 94%짜리 최강 신호가 꺼지고 있었음** |
| 압축폭탄·zip-slip 방어 추가 | 압축 크기만으로는 폭탄을 못 막음. 멤버 경로의 `..`·절대경로도 차단 |
| 아카이브 조회 실패를 `note`에 기록 | 실패가 조용히 "install script 없음"(-20점)이 되던 것. 보안 도구에서 **"모름"이 "깨끗함"이 되면 안 됨** |
| 없는 버전에 `note` 기록 | `requests==99.99.99` 가 아무 표시 없이 `found=True`로 통과하던 것 |
| lint 5건 자동수정 | main에 이미 반영 (`UP017`·`RUF022`·`F401`·`E501`) |

**호환성:** `collect()` 와 `score_package()` 에 `ctx=` 파라미터가 추가됐지만
**기존 호출 방식도 그대로 동작합니다.** 승준 님 테스트 15개 전부 무수정 통과 확인했습니다.

### 2-3. 승준 님이 판단하실 것 (제가 일부러 안 건드렸습니다)

#### 🔴 typosquat floor 0.90이 너무 높습니다 — 제일 급함

```
reqeusts    typosquat=0.88  →  score 26  →  safe   ⚠️ README 대표 예시
colourama   typosquat=0.94  →  score 40  →  warn
정상 최고    typosquat=0.73  (requests-toolbelt 등)
```

`HIGH_TYPOSQUAT = 0.90` floor가 `reqeusts`(0.88)를 못 잡습니다.
정상 패키지 최고값이 0.73이니 **0.73 ~ 0.90 사이가 빈 구간**인데, 하필 대표 예시가 거기 빠졌습니다.

0.80~0.85로 내리면 정상과도 여유(0.07~0.12)가 있습니다. 다만 **재현율/오탐 스윕까지 돌려서
정하신 값이라 제가 임의로 바꾸지 않았습니다.**

> 지금은 레이어 ②가 mock이 아니라서 이게 그대로 드러납니다.
> `reqeusts`는 PyPI에서 삭제된 상태라 메타데이터 신호가 0이고, 이름 신호만 남는데
> 그게 warn 문턱(40)을 못 넘습니다.

#### 🟡 `requires_dist`가 최신 버전 것입니다

`data["info"]` 는 요청한 버전이 아니라 **최신 버전**을 설명합니다.

```
requests==2.0.0  (2013년, 선언된 의존성 0개)
  → dependency_count = 4      ← 최신 requests의 의존성
```

sdist는 `releases.get(version)`으로 버전별로 정확히 가져오셨는데, 이것만 `info`에서 옵니다.
`dependency_count`는 가중치가 0이라 **점수엔 영향이 없고 표시값만 틀립니다.**
정확히 하려면 `/pypi/{name}/{version}/json` 추가 호출이 필요해서(요청 1회 증가) 판단을 남겼습니다.

#### 🟡 `compute_score`의 근거 문장이 버려집니다

```python
score, _reasons = compute_score(signals)   # reasons 폐기
return signals, score
```

**이건 승준 님 잘못이 아니라 제가 만든 스키마 문제입니다.** 계약이 `(RiskSignals, int)`라
자리가 없습니다. 그런데 승준 님이 쓰신

> "Name closely resembles a popular package (similarity 0.82, +25)"

가 지금 사용자에게 나가는

> "메타데이터 위험도 스코어 26점"

보다 훨씬 좋은 데모 재료입니다. 아래 회의 안건 1번으로 올립니다.

## 3. 민규 파트에서 나온 문제 (공유)

승준 님만 지적하면 불공평하니 제 쪽도 적습니다. **제 정적분석이 `requests`를 차단했습니다.**
PyPI 다운로드 1위 패키지를요.

```
setup.py:57  os.system("python setup.py sdist bdist_wheel")   ← publish 가드 안, 설치 때 안 돎
setup.py:58  os.system("twine upload dist/*")                 ← 같음
setup.py:79  exec(f.read(), about)                            ← __version__ 읽는 관용구
```

`eval`·`exec`·`os.system`을 전부 high로 잡은 게 원인이었습니다. 심각도 모델을 바꿨습니다:

> **위험 함수 호출은 판정 근거가 아니라 `정황`입니다.
> high는 "Python 코드에 흔한 것"이 아니라 "공급망 공격에 특유한 것"에만 씁니다.**

high로 남긴 셋 — `.pth` 자동실행 / `install`·`develop` 명령 탈취 / 디코딩→실행 체인 — 은
전부 이 프로젝트의 차별점과 정확히 겹칩니다.
**"이미 가진 코드를 실행"은 일상이고 "방금 디코딩한 것을 실행"은 malware**라는 구분입니다.

그리고 공용 fetcher에 **데드락**이 있었습니다. 프로젝트 조회와 아카이브 조회를 같은
비재진입 락으로 감쌌는데 아카이브 경로가 프로젝트를 필요로 해서, 모든 스캔이 멈췄습니다.
**테스트는 전부 통과하는데 실제 요청만 걸리는 종류**였습니다.

> **교훈: 단위 테스트만으로는 부족합니다.** 서로 실제 패키지로 한 번씩 돌려봐야 합니다.
